# Research: LLM Reasoning Fine-Tuning Pipeline

**Branch**: `001-llm-reasoning-finetuning` | **Date**: 2026-04-14
**Revision**: 2 (corrected for 30B model per competition rules)

## Base Model

**Decision**: Use `nvidia/NVIDIA-Nemotron-3-Nano-30B-A3B-BF16`

**Rationale**: Competition rules require the Nemotron-3-Nano-30B
model. This is a hybrid Mamba-2 + Transformer architecture with
MoE (Mixture of Experts): 30B total parameters, 3.5B active per
token. Architecture details:
- 52 layers: 23 Mamba-2 + 23 MoE + 6 Attention (GQA, 2 groups)
- MoE config: 128 routed experts + 1 shared expert per MoE layer,
  6 experts active per token
- Context: 256K default (up to 1M with special flag)
- Licensed under NVIDIA Nemotron Open Model License

The competition loads this model with vLLM and applies your LoRA
adapter for evaluation. You do not control inference parameters.

**Alternatives considered**:
- `nvidia/NVIDIA-Nemotron-3-Nano-4B-BF16`: 4B dense model. NOT
  the competition target — competition explicitly requires the
  30B MoE variant.
- `nvidia/NVIDIA-Nemotron-3-Nano-30B-A3B-FP8`: FP8 variant.
  Useful for inference but competition loads bf16 weights.
- `nvidia/NVIDIA-Nemotron-3-Nano-30B-A3B-NVFP4`: 4-bit variant.
  Useful for local QLoRA training base.

## Training Dataset

**Decision**: Use `nvidia/OpenMathReasoning` CoT solutions as
primary training data

**Rationale**: CC-BY-4.0 licensed (constitution-compliant). Contains
5.68M rows (49.5GB) across 306K unique math problems with:
- 3.2M Chain-of-Thought (CoT) solutions — **primary focus**
- 1.7M Tool-Integrated Reasoning (TIR) solutions — deprioritized
  (competition inference has no code execution)
- 566K GenSelect samples
- 193K additional problems

CoT solutions are prioritized because the competition uses greedy
decoding (temperature=0.0) with no code execution capability. TIR
solutions assume tool access not available at inference time.

Solutions generated by DeepSeek-R1 and QwQ-32B. This dataset was
used in NVIDIA's AIMO-2 Kaggle winning submission.

**Alternatives considered**:
- TIR solutions from OpenMathReasoning: Deprioritized since
  competition inference cannot execute code. May ablate later.
- Synthetic data from closed APIs: Constitution VI prohibits
  unless competition explicitly allows.
- GSM8K / MATH benchmarks: Smaller, likely in pretraining data.
  Useful for validation only.

## Fine-Tuning Approach

**Decision**: QLoRA (4-bit quantized base + bf16 LoRA, rank <= 32)

**Rationale**: Competition caps LoRA rank at 32. The 30B model in
bf16 requires ~60GB VRAM for weights alone — too tight for training
on 96GB. QLoRA reduces base model to ~15-17GB, leaving ~75GB for
optimizer states, activations, and batch processing.

VRAM budget with QLoRA:
- 4-bit base model: ~15-17 GB
- LoRA adapters (r=32, bf16): ~0.3 GB
- Optimizer states (AdamW): ~0.6 GB
- Activations (batch=4, seq=2048): ~4-6 GB
- **Total**: ~20-24 GB
- **Headroom on 96GB**: ~72-76 GB

The massive headroom allows larger batch sizes or longer sequences
if needed.

**Alternatives considered**:
- Full bf16 LoRA: Base model alone is ~60GB. With training
  overhead, likely exceeds 96GB with useful batch sizes. Risky.
- Full fine-tuning: Not applicable — competition requires LoRA
  adapter submission.
- fp8 base + bf16 LoRA: ~30GB base. Viable but 4-bit is better
  studied and PEFT/bitsandbytes support is mature.

## Inference Framework

**Decision**: Use vLLM for local evaluation (matching competition)

**Rationale**: The competition uses vLLM to load the base model
and apply LoRA adapters. Local evaluation MUST use the same engine
with identical parameters to avoid train/eval distribution mismatch.

Competition inference parameters (fixed, not tunable):
- temperature=0.0 (greedy decoding)
- top_p=1.0
- max_tokens=7680
- max_model_len=8192
- max_num_seqs=64
- gpu_memory_utilization=0.85
- max_lora_rank=32

**Alternatives considered**:
- SGLang: Also supported but competition uses vLLM. Must match.
- Native Transformers: Too slow for full benchmark evaluation.

## Answer Format

**Decision**: Train model to output answers in `\boxed{}` LaTeX

**Rationale**: The competition metric extracts the final answer from
`\boxed{}` format, falling back to heuristic patterns or last numeric
value. Training data MUST include `\boxed{}` in target outputs to
ensure reliable format compliance under greedy decoding.

## Validation Strategy

**Decision**: 5% held-out split from OpenMathReasoning, stratified
by difficulty

**Rationale**: Same-distribution validation with known ground truth.
5% of 306K problems = ~15K validation samples — large enough for
statistically meaningful comparisons. Stratification by difficulty
prevents overrepresentation of easy problems.

The competition metric (exact match or numerical tolerance 1e-4)
MUST be reimplemented locally for accurate validation.

## Training Pipeline

**Decision**: Hugging Face TRL SFTTrainer + PEFT for QLoRA

**Rationale**: TRL is the most portable and well-documented option
for LoRA/QLoRA SFT. It produces standard adapter_config.json files
compatible with vLLM LoRA loading. The competition accepts adapters
from any training framework.

**Alternatives considered**:
- NeMo-Skills: NVIDIA's pipeline. Useful for data filtering but
  heavier dependency for training. Use for data prep only.
- Unsloth: Fast LoRA training but Mamba-2 hybrid support unclear.
  Investigate if TRL proves too slow.
- Axolotl: Good config-driven approach. Viable alternative if TRL
  has issues with the MoE architecture.

## RL Follow-Up (Optional)

**Decision**: Plan SFT first, ablate RL (GRPO/DPO) as separate
experiment after validating SFT gains

**Rationale**: Per constitution principle III (iterative
experimentation), validate the simpler approach before adding
complexity. RL can optimize directly for correct final answers
within the constrained rank-32 adapter, potentially squeezing more
quality. But RL adds training instability and hyperparameter
sensitivity.

## Data Quality Filtering

**Decision**: Adapt NVIDIA's filtering approach from the
OpenMathReasoning paper

**Rationale**: Key filters for CoT solutions:
- Remove solutions with incorrect final answers
- Filter repetitive reasoning patterns (length-based heuristics)
- Ensure solutions end with `\boxed{}` format answer
- Prefer shorter correct solutions (efficiency within 7680 token
  limit)
- Balance domain coverage
- Filter solutions exceeding 7680 tokens (competition max_tokens)
